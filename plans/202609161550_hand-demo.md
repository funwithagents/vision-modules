# Hand demo and public API

**Status:** Done

Wires the four implemented concepts into something runnable: the package's public re-exports in `src/vision_modules/__init__.py`, and the `examples/hand_demo.py` demo, now specced on its own in [specs/hand_demo.md](../specs/hand_demo.md). The demo is a **Gradio browser app**: its streaming webcam component captures frames client-side and pushes them into the pipeline through a small `FrameSource` adapter, rather than `StreamProvider` opening a local camera device via `OpenCVSource`. This is a deliberate deviation from the plan's original `cv2.imshow` design (decided with the user 2026-09-16); the demo's design used to live as a paragraph inside `specs/pipeline.md`, then moved out to its own spec at the user's request.

## Context you need before starting

- Read `AGENTS.md` (project map — you will add a row), `specs/hand_demo.md` (the demo's own spec), `specs/pipeline.md` ("Concurrency rules"), `specs/stream.md` ("Frame ownership" and the injectable `FrameSource` seam).
- Prerequisites: plans `…1500` through `…1540` are all `Done`.
- The demo is an **application**: it is the only place that draws. There is no native GUI window and so no main-thread constraint (that constraint in `specs/pipeline.md` is specific to `cv2.imshow`/`cv2.waitKey`); the streaming callback draws the overlay and returns it to Gradio, which renders it in the browser. Worker threads inside the library still only compute and publish — they never build the callback's return value.
- `examples/` is **not** in pyright's `include`, but `uv run ruff check .` does lint it. Keep the script clean anyway (type hints on every function).
- `import vision_modules` must stay cheap: the package `__init__` re-exports from `hand` and `gesture_classifier`, which is fine **only because** those modules import `mediapipe` / `torch` lazily.
- Gradio delivers browser frames as RGB `uint8` arrays; the library's internal convention (following `cv2`) is BGR — convert at the boundary, both ways.

4. Create `examples/hand_demo.py`:

   ```
   usage: hand_demo.py [--mirror] [--hand-fps N] [--classifier-fps N] [--threshold T]
   ```
   - No `--source`: the browser's webcam picker chooses the camera, so there is no server-side device/file argument. `--mirror` flag. Defaults for the fps / threshold flags come from the spec (30, 5, 0.55).
   - A small `PushFrameSource` (implements `stream.py`'s `FrameSource` protocol) fed by the Gradio callback instead of `OpenCVSource`:
     ```python
     class PushFrameSource:
         """FrameSource fed by frames pushed from the Gradio streaming callback."""

         def __init__(self) -> None:
             self._slot: LatestValue[np.ndarray] = LatestValue()
             self._new_frame = threading.Event()
             self._closed = False

         def push(self, image_bgr: np.ndarray) -> None:
             self._slot.publish(image_bgr)
             self._new_frame.set()

         def read(self) -> np.ndarray | None:
             while not self._closed:
                 if self._new_frame.wait(timeout=0.1):
                     self._new_frame.clear()
                     return self._slot.get()
             return None

         def close(self) -> None:
             self._closed = True
             self._new_frame.set()
     ```
   - Build once: `source = PushFrameSource()`; `provider = StreamProvider(source, mirror=args.mirror)`; `hands = HandStage(provider, target_fps=args.hand_fps)`; `gestures = GestureClassifier(hands, target_fps=args.classifier_fps, threshold=args.threshold)`.
   - Streaming callback (BGR internally, RGB at the Gradio boundary both ways):
     ```python
     def on_frame(frame_rgb: np.ndarray) -> np.ndarray:
         source.push(cv2.cvtColor(frame_rgb, cv2.COLOR_RGB2BGR))
         frame = provider.latest()
         if frame is None:
             return frame_rgb
         canvas = frame.image.copy()  # NEVER draw on frame.image
         hr = hands.latest()
         gr = gestures.latest()
         if hr is not None:
             for i, hand in enumerate(hr.hands):
                 x0, y0, x1, y1 = hand.bbox
                 cv2.rectangle(canvas, (x0, y0), (x1, y1), (0, 255, 0), 2)
                 text = "..."  # classifier hasn't run yet
                 if gr is not None and i < len(gr.hands):
                     g = gr.hands[i]
                     text = f"{g.label or '?'} {g.confidence:.0%}"
                 cv2.putText(
                     canvas,
                     text,
                     (x0, max(y0 - 8, 16)),
                     cv2.FONT_HERSHEY_SIMPLEX,
                     0.7,
                     (0, 255, 0),
                     2,
                 )
             if not hr.hands:
                 cv2.putText(
                     canvas,
                     "no hand",
                     (10, 30),
                     cv2.FONT_HERSHEY_SIMPLEX,
                     0.8,
                     (128, 128, 128),
                     2,
                 )
         return cv2.cvtColor(canvas, cv2.COLOR_BGR2RGB)
     ```
   - Build the interface and launch it inside the pipeline's context manager, so `Pipeline.stop()` runs on server shutdown:
     ```python
     demo = gr.Interface(
         fn=on_frame,
         inputs=gr.Image(sources=["webcam"], streaming=True),
         outputs="image",
         live=True,
         flagging_mode="never",  # no review workflow here; don't dump frames to disk
     )
     with Pipeline([provider, hands, gestures]):
         demo.launch()
     ```
   - Print one line at start-up saying the model may download on first run.
   - `if __name__ == "__main__": main()`.

**Post-hoc revision (2026-09-16):** `tests/test_package.py` (the import-cost and public-name-resolution tests from step 2's original scope) was removed after review — the user judged both tests too thin to keep. `import vision_modules` staying cheap (no eager `mediapipe`/`torch`) is no longer covered by an automated test; that invariant now relies on `hand.py`/`gesture_classifier.py` keeping their heavy imports inside functions, unguarded.

**Post-hoc revision (2026-09-16), UI redesign:** step 4's `gr.Interface` + on-image `cv2.putText` overlay (shown above) was replaced with a `gr.Blocks` layout, because gesture text drawn on the video was hard to read. Current design, see [specs/hand_demo.md](../specs/hand_demo.md) for the settled spec:
- A `gr.Slider` (0–1, default `args.threshold`) sits above the webcam component and live-updates `gestures.threshold` on `.change()` — no restart needed to retune.
- The webcam image now only gets the green hand bounding box (`draw_boxes`) — no text is drawn on it.
- Below the image, a right-hand panel (an empty spacer `gr.Column` + a real one, side by side in a `gr.Row`) holds a `gr.Label` (full per-class score breakdown, "detected classifications") and a `gr.Textbox` (the thresholded call — the label if its score cleared the threshold, else `"none"`, or `"no hand"` / `"..."` while there's nothing to classify yet).
- `cam.stream(fn=on_frame, inputs=cam, outputs=[cam, scores, validated])` replaces `gr.Interface(fn=on_frame, ...)`; `on_frame` now returns a 3-tuple. `flagging_mode="never"` is moot — `gr.Blocks` never adds a Flag button (that was an `Interface`-only default), so this simplifies the Interface variant's earlier fix rather than needing to be re-applied.

**Post-hoc revision (2026-09-16), 3-column layout:** the single self-feeding `cam` component (looping the annotated frame back into the same webcam widget) was replaced with two separate `gr.Image`s — `cam_in` (raw browser feed) and `cam_out` (output-only, bbox overlay) — because the user wanted the raw and annotated views visible side by side, as they'd been with the original `gr.Interface`. The separate `validated` `gr.Textbox` was also dropped: `summarize()` now returns a single `dict[str, float]` for the `gr.Label`, prefixing the validated class's key with a checkmark (`✓`) when `HandGesture.label` cleared the threshold — `gr.Label` already sorts by score, so the top-scoring class is always the top row, and the checkmark is the only extra signal needed. Current layout is one `gr.Row` of three columns (Input / Detected / Classifications) below the threshold slider. See [specs/hand_demo.md](../specs/hand_demo.md) for the settled spec.

**Post-hoc revision (2026-09-16), real vs. target fps:** the user asked whether achieved hand/classifier fps can differ from `--hand-fps`/`--classifier-fps` (yes — it's a ceiling, capped further here by `cam_in.stream()`'s `stream_every`, which was left at Gradio's `0.5`s/2fps default and so was silently bottlenecking the whole pipeline regardless of the CLI flags; now set to `1 / args.hand_fps`) and whether the real numbers could be shown. Added `FpsMeter` (`examples/hand_demo.py`): `(frame_id_now - frame_id_last) / (t_now - t_last)` between any two samples of a stage's `frame_id`, exact because `frame_id` is strictly increasing and published once per processed item — no tight polling loop needed. A `gr.Timer(1.0)` ticks once a second, sampling `hands.latest()`/`gestures.latest()` through one `FpsMeter` each, and updates a `gr.Markdown` under the threshold slider with both real numbers next to their targets. See [specs/hand_demo.md](../specs/hand_demo.md) ("Real vs. target fps").

**Post-hoc revision (2026-09-17), live fps sliders:** the user then asked whether `target_fps` could be changed from the UI too, or only at construction. It's the latter's opposite — `Stage.target_fps` is a plain mutable attribute [pipeline.md](../specs/pipeline.md) reads fresh every worker-loop iteration (never cached), exactly like `GestureClassifier.threshold`, so it's just as live-adjustable. Added `hand_fps`/`classifier_fps` `gr.Slider`s next to the threshold slider (all three now in one `gr.Row`), each `.change()`-wired to set `hands.target_fps`/`gestures.target_fps` directly — no pipeline-side change needed. Noted the one real limit: raising the hand-fps slider above the launch-time value can't get more frames out of the browser, since `cam_in.stream()`'s `stream_every` is fixed at launch from the initial `--hand-fps`; the fps readout added in the previous revision makes that cap visible regardless. Also fixed `on_fps_tick`'s displayed "target" to read `hands.target_fps`/`gestures.target_fps` live rather than the stale `args.hand_fps`/`args.classifier_fps`, so it tracks the sliders. See [specs/hand_demo.md](../specs/hand_demo.md) ("Layout: `gr.Blocks`, not `gr.Interface`").

**Post-hoc revision (2026-09-17), shared fps slider scale:** the hand-fps and classifier-fps sliders originally had different ranges (1–max(60, hand default), 1–max(30, classifier default)), inherited from their different CLI defaults (30 vs. 5). The user asked for one shared scale so the two are directly comparable; both now use `minimum=1, maximum=max(30.0, args.hand_fps, args.classifier_fps)`.
